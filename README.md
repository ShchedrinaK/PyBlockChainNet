# PyBlockchain-Network: Proof-of-Work Consensus

Легковесная распределенная блокчейн-сеть, реализованная на Python. Проект демонстрирует базовую механику консенсуса **Proof-of-Work (PoW)**, синхронизацию узлов (P2P) и защиту от подделки данных (Tamper-resistance). 

Данная реализация эмулирует многопоточную среду, где несколько узлов одновременно пытаются добыть новый блок, разрешая конфликты (Race Conditions) по правилам сети.

## Основные возможности (Features)

*   **Proof-of-Work (PoW):** Настраиваемая сложность майнинга (difficulty) для защиты от спама и регулирования скорости создания блоков.
*   **Криптографическая целостность:** Использование SHA-256 для связывания блоков через `previous_hash`.
*   **Эмуляция сети:** Многопоточная симуляция узлов, которые обмениваются блоками и разрешают конфликты.
*   **Защита от атак:** Автоматическая валидация блоков, отбрасывание устаревших цепочек и обнаружение изменений в истории (Fork resolution).
*   **Прозрачность:** Подробное логирование всех процессов (майнинг, принятие/отклонение блоков) в консоль.

## Архитектура

Проект состоит из трех основных компонентов, разделенных по зонам ответственности:

1.  **`Block` (Блок)**
    Содержит данные (`data`), временную метку (`timestamp`), индекс (`index`), хеш предыдущего блока (`previous_hash`) и случайное число для майнинга (`nonce`). Метод `calculate_hash()` генерирует уникальный SHA-256 оттиск.
2.  **`Blockchain` (Цепочка)**
    Управляет списком блоков (Ledger). Отвечает за настройку уровня сложности (`difficulty`), добавление новых блоков и валидацию всей цепочки (`is_valid()`).
3.  **`Node` (Узел сети)**
    Представляет отдельного участника сети. Узел умеет майнить блоки (`mine_block`), рассылать их пирам (`broadcast`) и принимать входящие блоки от других узлов, проверяя их валидность.

## Сценарии работы и симуляция

При запуске скрипта автоматически воспроизводятся два сценария, демонстрирующие поведение сети.

### Сценарий 1: Разрешение конфликтов (Race Condition)
Сеть из трех узлов (A, B, C) одновременно начинает майнить блок с индексом 1. 

**Что происходит:**
1. Узлы начинают перебор `nonce`.
2. Узел B первым находит валидный хеш (начинается на `0000...`) и моментально рассылает его пирам.
3. Узлы A и C принимают блок от B, так как он валиден.
4. Через некоторое время узлы A и C тоже находят свои решения, но **отклоняют собственные блоки**, так как сеть уже ушла вперед (цепочка обновилась). 

```text
=== Симуляция одновременного майнинга ===
Узлы А, В и С одновременно пытаются намайнить блок с index=1 (сложность 4)...
[Узел В] УСПЕШНО намайнил блок 1! Nonce: 8849
[Узел В] Добавил блок в свою цепочку. Распространяет...
[Узел А] ПРИНЯЛ блок 1 от сети.
[Узел А] УСПЕШНО намайнил блок 1! Nonce: 40840
[Узел С] ПРИНЯЛ блок 1 от сети.
[Узел А] ОТКЛОНЯЕТ свой блок: пока майнили, сеть ушла вперед (race condition).
[Узел С] УСПЕШНО намайнил блок 1! Nonce: 200009
[Узел С] ОТКЛОНЯЕТ свой блок: пока майнили, сеть ушла вперед (race condition).
```

### Сценарий 2: Тест на защиту от подделки (Tamper-resistance)
Симуляция попытки злоумышленника изменить данные в уже существующем блоке.

**Что происходит:**
1. Данные в блоке 1 (например, сумма транзакции) изменяются напрямую.
2. При попытке валидации сети метод `is_valid()` возвращает `False`, так как пересчитанный хеш перестает удовлетворять условиям PoW.
3. Скрипт демонстрирует процесс перемайнинга (пересчета) всей цепочки с измененного блока, чтобы показать вычислительную сложность такой атаки.

```text
=== Проверка защиты от подделки ===
[Взлом] Изменяем данные в блоке 1...
Ошибка: Хеш блока 1 не соответствует данным.
Валидность цепочки после подделки (без перемайнинга): False
```

## Безопасность и особенности реализации

*   **Асимметрия PoW:** Задача майнинга трудоемка для поиска (требует перебора тысяч `nonce`), но тривиальна для проверки (достаточно одного вызова `calculate_hash()`). Это основа защиты сети от спама.
*   **Защита от 51% атаки:** Перезапись истории (перемайнинг цепочки) требует контроля над более чем 50% вычислительной мощности всей сети. Чем длиннее цепочка и выше `difficulty`, тем дороже атака.
*   **Криптостойкость:** Используется SHA-256. Использование некриптографических хешей (например, CRC32) недопустимо, так как они подвержены коллизиям, что позволило бы легко подделывать блоки.
*   **Race Conditions:** В распределенных системах нет "глобальных часов". Если два узла нашли блок одновременно, сеть разрешает конфликт по правилу "самая длинная цепочка побеждает" (или "первый валидный блок, удлиняющий нашу цепочку"). Узлы автоматически отбрасывают устаревшие ветки.
